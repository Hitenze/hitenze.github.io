Essential HPC Resource Concepts

Before diving into job scheduling, it's crucial to understand the fundamental resources you'll be requesting. These concepts form the foundation of every HPC job submission.

Physical Resources

Node --nodes

A complete computer in the cluster with its own processors, memory, and often local storage. Think of it as one physical machine in a rack.

Example: A node might have 64 CPU cores, 256GB RAM, 2 GPUs

CPU slot --cpus-per-task

A schedulable CPU unit assigned to a task. It is often a physical core, but a cluster may configure it as a hardware thread.

Check lscpu, scontrol show node, and your site's documentation before assuming the topology.

GPU --gres=gpu

Accelerator resources for parallel computation. This guide uses a whole-GPU request as its portable baseline; some sites expose typed GPUs, MIG instances, or shared GPU resources.

Inspect the local Slurm configuration and site documentation before choosing a GPU request.

Memory --mem

RAM available for your job. --mem requests memory per node; alternatives such as --mem-per-cpu and --mem-per-gpu use different scopes and are mutually exclusive with it.

Units: MB (default), GB (with G suffix)

Logical Resources

Task --ntasks

An independent process (instance of your program). For MPI jobs, each task is an MPI rank. Tasks can span multiple nodes.

Default: 1 task is assigned 1 schedulable CPU slot

Partition --partition

Logical grouping of nodes with similar characteristics or policies. Also called "queue" in some systems.

Examples: standard, gpu, highmem, debug

Job --job-name

Your complete workload submission, including all resource requests and the script/program to run.

Types: Batch (sbatch), Interactive (srun), Allocation (salloc)

Time --time

Wall-clock time limit for your job. Jobs are terminated when this limit is reached, so always add a buffer.

Format: DD-HH:MM:SS or HH:MM:SS

Critical Resource Relationships

Common Full-Node Layout

Requested CPU slots = nodes × tasks-per-node × CPUs-per-task

This describes a common explicit layout. The application still has to create the matching processes and threads, and the cluster may allocate CPUs as cores or hardware threads.

MPI Jobs (Distributed Memory)
--ntasks=32
--cpus-per-task=1

32 independent processes, each with 1 CPU slot

OpenMP Jobs (Shared Memory)
--ntasks=1
--cpus-per-task=32

1 process with 32 threads on same node

Common Resource Request Patterns

Serial Job

#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --mem=4G

Single process, single thread

Pure MPI

#SBATCH --nodes=4
#SBATCH --ntasks-per-node=32
#SBATCH --cpus-per-task=1
#SBATCH --mem=128G

128 MPI processes; 128 GB per node, 512 GB total

Pure OpenMP

#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=64
#SBATCH --mem=128G

1 process with 64 threads; 128 GB on its node

Hybrid MPI+OpenMP

#SBATCH --nodes=4
#SBATCH --ntasks-per-node=2
#SBATCH --cpus-per-task=32
#SBATCH --mem=128G

8 MPI ranks, 32 threads each; 128 GB per node, 512 GB total

GPU Job

#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=8
#SBATCH --gres=gpu:1
#SBATCH --mem=64G

1 GPU with 8 schedulable CPU slots

Array Job

#SBATCH --array=1-100%10
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=4

100 similar jobs, max 10 concurrent

Site-specific GPU syntax: this guide uses --gres=gpu:1 as its baseline. Some clusters prefer --gpus-per-task=1, which requires an explicit task layout and compatible Slurm configuration. Follow the local scheduler documentation.

Common Mistakes & Myths

Memory limit

Myth: The system will give more memory if I need it.

Reality: If your job uses more than you requested, it gets killed (OOM).

Time limit

Myth: Jobs run until they finish.

Reality: When the time limit is reached, the scheduler cancels the job.

Wrong partition

Myth: Any partition is fine.

Reality: Partitions map to different hardware/policies; the wrong one can wait forever or fail (e.g., GPU job in a CPU queue).

“More nodes = faster”

Myth: Adding nodes always speeds things up.

Reality: Only distributed programs benefit; extra nodes add communication overhead and can be slower.

The Role of a Job Scheduler

The Slurm Workload Manager, historically named the Simple Linux Utility for Resource Management, orchestrates the efficient, fair, and orderly allocation of computational resources across hundreds or thousands of users and jobs.

Resource Management

Tracks CPU slots, memory, GPUs, nodes (and other GRES).

Job Queuing

Fair-share, priority, and backfill to keep the cluster busy.

Quality of Service

Policies/limits to prevent monopolization (time, cores, GPUs, jobs).

Core commands / inspect before guessing

Essential Slurm Commands

sbatch job.slurm

Submit a batch script and record the returned job ID.

squeue -u $USER

Inspect pending and running jobs without repeatedly polling every second.

scontrol show job JOBID

See requested resources, state, placement, and pending reason.

sacct -j JOBID

Review elapsed time, exit status, and accounting data after a job starts or finishes.

scancel JOBID

Cancel only the job you intend to stop; verify the ID first.

sinfo -s

Summarize partitions and availability; names and policies remain site-specific.

Interactive Jobs: Real-Time Computing

Interactive jobs provide real-time access to compute resources, perfect for development, debugging, and exploratory data analysis. Unlike batch jobs that run unattended, interactive jobs let you work directly on powerful compute nodes.

Interactive Jobs

  • Real-time command execution and feedback
  • Perfect for debugging and development
  • Immediate resource allocation when available
  • Interactive data exploration and visualization

Best for: Development, debugging, testing, data exploration

Batch Jobs

  • Run unattended without user interaction
  • Ideal for production runs and long computations
  • Output saved to files for later review
  • Can queue and wait for resources

Best for: Production runs, overnight jobs, parameter sweeps

Common Interactive Job Commands

Direct Interactive Session (srun)

# Basic interactive shell
srun --pty --time=01:00:00 bash
# With specific resources
srun --mem=16G --cpus-per-task=4 --pty bash
# GPU interactive session
srun --gres=gpu:1 --time=02:00:00 --pty bash

Immediate interactive access to compute node

Resource Allocation (salloc)

# Allocate resources
salloc --nodes=2 --time=02:00:00
# Then run commands
srun hostname
srun ./my_program
# Exit to release
exit

Allocate resources for multiple srun commands

Common Interactive Applications

Jupyter Notebook

srun --time=02:00:00 --mem=16G --pty bash
# Inside the allocated shell:
jupyter lab --no-browser --ip=127.0.0.1 --port=8888

Then use the site's Open OnDemand or documented SSH tunnel path.

Python with GPU

srun --gres=gpu:1 --time=01:00:00 --pty python

R Session

srun --mem=8G --time=01:00:00 --pty R

MATLAB

srun --cpus-per-task=4 --pty matlab -nodisplay

Important Considerations

  • A foreground interactive command may end if the connection drops
  • Resources charged even when idle
  • Limited to shorter walltimes
  • Use batch jobs for production runs
