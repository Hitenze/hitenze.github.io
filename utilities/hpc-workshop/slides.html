Module 01 / Core

Why HPC?

Scale the work, not just the machine.

01.1 / Parallel work

Expose independent work

Parallel hardware helps only when the algorithm provides work that can proceed concurrently.

More resources do not repair serial dependencies, load imbalance, or excessive communication.

01.2 / Execution models

Serial and parallel are algorithm choices

Serial

  • One ordered stream of work
  • Simple dependencies
  • Limited by one execution path

Parallel

  • Threads, processes, accelerators, or jobs
  • Requires partitioning and coordination
  • Limited by serial work and overhead

01.3 / Amdahl's Law

The serial fraction sets the ceiling

S(N) = 1 / ((1 - f) + f / N)

Example

If 95% of a program is parallel, 32 workers give at most about 12.5x speedup.

Limit

Even infinitely many workers cannot exceed 20x while 5% remains serial.

Optimize the dominant serial and communication costs before requesting a larger allocation.

01.4 / Scientific workloads

HPC is an end-to-end system

Simulation

PDEs, particles, climate, fluids, and materials.

Data

Genomics, imaging, inverse problems, and ensembles.

Learning

Training, inference, parameter sweeps, and uncertainty.

Compute, memory, storage, and communication must all fit the workload. The June 2026 TOP500 snapshot is linked from the field manual.

Module 02 / Core

Cluster Architecture

Know where each kind of work belongs.

02.1 / System map

A cluster has distinct operational zones

Laptop→Login node→Scheduler→Compute node(s)

Login

Edit, transfer, inspect, and submit.

Compute

Run CPU, GPU, and high-memory work.

Storage

Home, project, scratch, and archive have different policies.

02.2 / Login boundary

The login node is a control plane

Appropriate

  • Small edits and static checks
  • File transfer and Git
  • sbatch, squeue, sacct

Move to an allocation

  • Training and simulation
  • Large builds or test suites
  • Data processing and notebooks

VS Code Server, remote extensions, and agent terminals run on the remote login host too.

02.3 / Node anatomy

Resource topology matters

CPU

Sockets, cores, hardware threads, caches, and NUMA domains.

Memory

Capacity and bandwidth are node-local constraints.

GPU

Accelerators have model-specific memory and interconnects.

Inspect the site's node definitions before translating “CPU” into a physical core or hardware thread.

02.4 / Data path

Storage and networks are part of performance

Storage policy

HOMECode and small persistent files
PROJECTShared durable research data
SCRATCHFast temporary working data; purge policies apply

Communication

Interconnect latency and bandwidth matter for MPI, distributed training, and parallel I/O.

Local GPU links and the cluster fabric solve different communication problems.

Module 03 / Core

Scheduling with Slurm

Describe resources, submit work, inspect evidence.

03.1 / Scheduler role

The scheduler matches requests to resources

Jobs wait until compatible CPU, GPU, memory, time, and policy constraints are available.

A pending job is not necessarily broken. Inspect its reason before changing the request.

03.2 / Resource language

Request what the program can use

Tasks

--ntasks usually maps to processes or ranks.

CPU slots

--cpus-per-task reserves schedulable CPU units for each task.

Memory

--mem is per node, not a job-wide total.

GPU

--gres=gpu:1 is the generic baseline used here.

Time

--time is a hard wall-clock limit.

Site policy

Account and partition remain cluster-specific.

03.3 / Common layouts

Slots describe capacity, not utilization

requested CPU slots = nodes × tasks per node × CPUs per task

MPI

Many tasks, usually one or a few CPU slots each.

Threads

One task, multiple CPU slots, matching thread controls.

Hybrid

Several tasks, each with multiple threads.

Your application must create the matching ranks or threads. Slurm does not parallelize it automatically.

03.4 / Batch script anatomy

A conservative baseline

#!/bin/bash
#SBATCH --job-name=hello_hpc
#SBATCH --output=hello_hpc_%j.out
#SBATCH --error=hello_hpc_%j.err
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --mem=1G
#SBATCH --time=00:05:00

set -euo pipefail

# Add account, partition, and a Python module only when required.
cd "${SLURM_SUBMIT_DIR:-$PWD}"
python3 -u hello_hpc.py

Leave account and partition unset unless the local documentation requires them.

03.5 / Essential commands

Inspect before guessing

sbatch

Submit a batch script.

squeue

Inspect queued and running jobs.

scontrol

Explain job and node state.

sacct

Read state, time, memory, and exit code.

scancel

Stop a job intentionally.

sinfo

Summarize partitions and availability.

03.6 / Failure evidence

Diagnose from records, not anecdotes

sacct -j 12345 --format=JobID,State,Elapsed,MaxRSS,ExitCode
scontrol show job 12345
tail -n 80 hello_hpc_12345.out
tail -n 80 hello_hpc_12345.err

OUT_OF_MEMORY

Measure peak use; fix the program or right-size memory.

TIMEOUT

Estimate runtime or checkpoint; do not request arbitrary days.

PENDING

Read the reason: resources, dependency, policy, or reservation.

Module 04 / Core

Workflow and Tools

Reproducible environments, safe remote work, bounded automation.

04.1 / Python 3.12 + uv

Lock the project, not the login node

module spider python
module load python/<site-version>

uv init --python 3.12 myproject
cd myproject
uv add numpy scipy matplotlib
uv sync --locked
uv run --frozen python analysis.py

git add pyproject.toml uv.lock
echo ".venv/" >> .gitignore

Conda or Mamba remains useful for site-provided MPI, CUDA, or compiled dependency stacks.

04.2 / Remote-SSH

Connect in a terminal first

Host research-cluster
  HostName login.example.edu
  User your_username
  IdentityFile ~/.ssh/id_ed25519
  ServerAliveInterval 60
  # ProxyJump gateway.example.edu

Safe path

  1. Verify ssh research-cluster.
  2. Complete MFA.
  3. Open $HOME/project-name, not all of home.
  4. Run heavy work through Slurm.
  5. Forward Jupyter ports; never expose them publicly.

04.3 / Safe agentic workflow

Automation stops before submission

Plan→Validate→Smoke-test→Submit→Inspect

Agent may

  • Draft and explain scripts
  • Run static checks
  • Summarize .out, .err, and sacct

Requires approval

  • sbatch or scancel
  • Account and partition choices
  • Secrets or private data access

Review git diff before submitting anything the agent changed.

Module 05 / Core

Your First Job

Make one small claim and collect the evidence.

05.1 / Program

Dependency-free Python smoke test

# Abridged: use the full reviewed file in the field exercise
import os
import platform
import socket

def slurm_value(name):
    return os.environ.get(name, "not set")

work_items = 250_000
checksum = sum((i * i) % 97 for i in range(work_items))

print("=== HPC environment ===")
print(f"Hostname: {socket.gethostname()}")
print(f"Python: {platform.python_version()}")
print(f"Slurm job ID: {slurm_value('SLURM_JOB_ID')}")
print(f"Slurm node list: {slurm_value('SLURM_JOB_NODELIST')}")
print(f"CPU slots for task: {slurm_value('SLURM_CPUS_PER_TASK')}")
print(f"Deterministic checksum ({work_items:,} items): {checksum}")

05.3 / Validation sequence

Cheap checks first

bash -n→sbatch --test-only→small sbatch→sacct + logs 
bash -n hello_hpc.slurm

sbatch hello_hpc.slurm
squeue -u "$USER"

cat hello_hpc_12345.out
cat hello_hpc_12345.err

Appendix A / NumPy threads

Match BLAS threads to CPU slots

#SBATCH --ntasks=1
#SBATCH --cpus-per-task=4

export OMP_NUM_THREADS="$SLURM_CPUS_PER_TASK"
export OPENBLAS_NUM_THREADS="$SLURM_CPUS_PER_TASK"
export MKL_NUM_THREADS="$SLURM_CPUS_PER_TASK"
export NUMEXPR_NUM_THREADS="$SLURM_CPUS_PER_TASK"
uv run --frozen python -u numpy_threads.py

Benchmark 1, 2, and 4 threads. More threads can lose to startup, memory bandwidth, or nested parallelism.

Appendix B / Git

Capture code and environment, not generated data

project/
├── pyproject.toml
├── uv.lock
├── src/
├── scripts/
├── tests/
└── .gitignore    # .venv/, outputs/, large data

Commit scripts and lockfiles. Record the commit ID with each production run.

Appendix C / Data

Stage, compute, retain

Project storage→Scratch→Compute→Validated results→Archive
  • Check quota, purge, backup, and retention policies.
  • Do not treat scratch as durable storage.
  • Move many tiny files in archives or containers when appropriate.
Appendix D / Containers

Use the runtime supported by the site

apptainer pull python_3.12.sif docker://python:3.12-slim
apptainer exec python_3.12.sif python --version
sbatch --job-name=analysis \
  --time=00:30:00 --mem=4G --cpus-per-task=1 \
  --output=analysis_%j.out --error=analysis_%j.err \
  --wrap='apptainer exec myapp.sif ./run_analysis'

GPU, MPI, filesystem binding, and image-cache behavior remain site-specific.

Appendix E / Jupyter

Run the kernel in an allocation

# On the allocated compute node
jupyter lab --no-browser --ip=127.0.0.1 --port=8888

# From the laptop, if direct compute-node SSH is permitted
ssh -N -J research-cluster \
  -L 8888:127.0.0.1:8888 your_username@compute-node

Use the allocated hostname. Otherwise follow the site's Open OnDemand or documented relay-tunnel pattern.

Appendix F / Remote-SSH troubleshooting

Start below the IDE

  1. Run ssh -vv research-cluster in a terminal.
  2. Confirm host, username, key, MFA, and ProxyJump.
  3. Check whether rotating login nodes require ControlMaster.
  4. Remove stale VS Code Server state only after reviewing site guidance.
