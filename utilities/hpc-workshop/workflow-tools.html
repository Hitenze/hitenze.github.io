Environment Management

Module System

Dynamic environment management

The module system provides a clean way to manage multiple versions of software packages and their dependencies. 

# List available modules
module avail

# Discover versions on this cluster
module spider gcc

# Load a site-provided version
module load gcc/<site-version>

# Load multiple modules
module load openmpi python

# Show loaded modules
module list

# Unload all modules
module purge

Best Practices:

  • • Record exact module names and versions for reproducibility
  • • Use module purge only when your site's documentation recommends it
  • • Document module requirements in your scripts
  • • Test with different compiler versions

Python Environments

Python 3.12 projects with uv

Manage Python packages and dependencies in isolated environments to avoid conflicts and ensure reproducibility.

Recommended uv Project:

# Use a site module or an approved uv installation
module load python

# Create a Python 3.12 project and lock dependencies
uv init --python 3.12 myproject
cd myproject
uv add numpy scipy matplotlib

# Recreate and run the locked environment
uv sync --locked
uv run --frozen python analysis.py

What to Commit

Commit pyproject.toml and uv.lock. Put .venv/ in .gitignore.

Conda or Mamba remains useful when a site distributes MPI, CUDA, or other compiled stacks through Conda. Do not mix package managers in one environment without a specific reason.

Install uv only through your institution's approved method or the official installation guide; this tutorial intentionally avoids piping remote scripts into a shell.

Remote Development

VS Code Remote-SSH

Professional remote development environment

Recommended Approach

VS Code Remote-SSH provides a seamless development experience with full IDE functionality on HPC systems.

Setup Steps:

1

Verify SSH in a terminal

ssh user@cluster.example.edu must work before debugging VS Code.

2

Install Remote-SSH

Install Microsoft's Remote-SSH extension in VS Code.

3

Configure the host

Open the SSH configuration file and add a short host alias.

4

Connect and open a project

Open a specific project directory, not your entire home directory.

Minimal ~/.ssh/config

Host my-cluster
    HostName cluster.example.edu
    User your_username
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 60

# If your institution requires a jump host:
# ProxyJump your_username@login.example.edu

Benefits:

  • • Full IDE experience on remote systems
  • • Integrated terminal and file explorer
  • • IntelliSense and debugging support
  • • Extension support for languages and tools

Terminal Editors

Lightweight command-line editing

Nano

Beginner-Friendly

Simple editor with on-screen help

nano filename.txt
Ctrl+X to exit, Ctrl+O to save

Vim

Powerful

Modal editor with extensive features

vim filename.txt # Open file

:wq # Save and quit

Quick Vim Survival Guide:

i - Insert mode
Esc - Normal mode
:w - Save file
:q - Quit
dd - Delete line
u - Undo
Login-node boundary: the VS Code server, remote extensions, terminals, and coding agents run on the remote login host. Keep extensions lightweight and use srun, salloc, or sbatch for computation. MFA and rotating login nodes can require site-specific configuration; on macOS/Linux, SSH connection sharing with ControlMaster can help when two VS Code connections otherwise land on different hosts. Use VS Code's Ports view or SSH forwarding for Jupyter instead of exposing notebook servers publicly. 
# On the allocated compute node
jupyter lab --no-browser --ip=127.0.0.1 --port=8888

# From the laptop, when direct compute-node SSH is permitted
ssh -N -J my-cluster \
  -L 8888:127.0.0.1:8888 your_username@compute-node

Replace compute-node with the allocated hostname. If compute-node SSH is disabled, use the site's documented Open OnDemand or relay-tunnel workflow instead; do not expose Jupyter on a public interface.

Research-Specific Best Practices

Repository Structure:

project/
├── src/ # Source code
├── data/ # Small datasets
├── scripts/ # Analysis scripts
├── results/ # Generated outputs
├── docs/ # Documentation
├── pyproject.toml
├── uv.lock
└── README.md

Commit Message Guidelines:

  • • Use present tense: "Add feature" not "Added feature"
  • • Be specific about changes and their purpose
  • • Reference issues or experiments when relevant
  • • Include performance impact if significant

What NOT to Commit:

  • • Large datasets (use Git LFS or external storage)
  • • Compiled binaries and temporary files
  • • Personal configuration files
  • • Sensitive information (passwords, keys)

Optional reference / troubleshooting

Getting Help from HPC Support

Quick self-checks and what to send for faster resolution.

Try this first (≤5 min)

  • • Open .out/.err; search for OUT OF MEMORY, TIME LIMIT, command not found
  • • Check pending reason or failure cause
squeue -j <JOBID> -o "%.18i %.9P %.20j %.2t %.10M %.6D %R"

When to open a ticket

  • • Self‑check done; still failing or inconsistent
  • • Account/quota/permission issues
  • • Suspected node/filesystem problems

What to include

  • • Username; cluster/partition; JobID(s)
  • • How you ran it (batch / interactive)
  • • Job script and submit command
  • • Error lines from .out/.err
  • • Minimal repro if possible
  • • Environment (module list / env name; GPU model)

Handy commands

squeue -u $USER
tail -n 50 job_<JOBID>.out
sinfo -s

Optional reference / portable workflows

Modern HPC Practices

Containers with Apptainer

Reproducible software environments

Containers package applications and dependencies for consistent execution across different HPC systems.

Benefits:

  • • Reproducible software environments
  • • Easy software distribution
  • • Bypass dependency conflicts
  • • Run legacy software on modern systems

Basic Apptainer Usage:

# Pull container from Docker Hub
apptainer pull python_3.12.sif docker://python:3.12-slim

# Run interactive shell
apptainer shell python_3.12.sif

# Execute command in container
apptainer exec python_3.12.sif python my_script.py

# Submit a bounded container job
sbatch --job-name=analysis \
  --time=00:30:00 --mem=4G --cpus-per-task=1 \
  --output=analysis_%j.out --error=analysis_%j.err \
  --wrap='apptainer exec myapp.sif ./run_analysis'

Some sites still expose the legacy singularity command. Container availability, bind mounts, and registry access are site-specific.

Workflow Management

Automate complex analysis pipelines

Workflow management systems automate complex computational pipelines with dependency tracking and error handling.

Snakemake

Python-based

Python-based workflow management with automatic parallelization

# Simple Snakemake rule
rule process_data:
    input: "data/{sample}.txt"
    output: "results/{sample}.out"
    shell: "process_script.py {input} {output}"

Nextflow

Container-native

Scalable and portable workflows with native container support

# Nextflow process
process analyze {
    input: path(datafile)
    output: path("result.txt")
    """
    analyze_tool $datafile > result.txt
    """
}

Workflow Advantages:

  • • Automatic dependency resolution
  • • Parallel execution optimization
  • • Resume failed runs from checkpoints
  • • Portable across different clusters

Optional reference / guarded automation

Safe Agentic HPC Workflow

Use an agent to prepare and check work, not to bypass scheduler policy.

Plan → Validate → Smoke-test → Submit → Inspect

  1. Ask the agent to read the project rules and explain assumptions before editing.
  2. Generate the script without running sbatch or scancel.
  3. Review git diff, then run bash -n job.slurm and sbatch --test-only job.slurm when available.
  4. Submit a short, small-resource smoke job only after human approval.
  5. Diagnose from stdout, stderr, and sacct; do not guess or silently request more resources.

Example AGENTS.md Rules

- Never run compute-heavy commands on login nodes.
- Do not call sbatch or scancel without explicit approval.
- Treat account, partition, and GPU type as site-specific.
- Validate scripts before suggesting submission.
- Never read, print, or commit secrets or private data.

Prompt pattern

“Read AGENTS.md and this Slurm script. Do not submit jobs. Prepare a 30-minute, 1-GPU smoke job, leave site-specific fields unset, run static validation, and summarize every assumption.”

Optional reference / storage lifecycle

Data Management Best Practices

Efficient File Transfer

The paths below illustrate common roles. Replace them with the working and retained-storage paths documented by your site.

SCP (Secure Copy)

# Upload to cluster
scp -r local_dir/ user@cluster:/scratch/project/

# Download from cluster
scp user@cluster:/home/results.tar.gz ./

Rsync (Efficient Sync)

# Sync directories (only transfer changes)
rsync -avz --progress local_dir/ user@cluster:/project/

# Resume interrupted transfers
rsync -avz --partial --progress large_file user@cluster:/scratch/

Globus (Large-scale Transfer)

Web-based service for reliable, high-speed transfer of large datasets between institutions.

Storage Strategy

Critical Data Management Rules

  • • Never rely solely on temporary or purgeable storage for important data
  • • Backup results immediately after job completion
  • • Use the site's protected project storage for retained collaborative data
  • • Monitor quota usage regularly

Data Lifecycle:

Input: Stage data in the site's recommended working filesystem
Processing: Use scratch only when its policy fits the workload
Results: Copy validated outputs to protected project storage
Archive: Move retained outputs to approved archival storage
Cleanup: Remove temporary files according to site policy

Automation Script Example:

#!/bin/bash
# Capture the application status in the batch script
uv run --frozen python analysis.py
status=$?

if [ "$status" -eq 0 ]; then
    archive_dir="${PROJECT_RESULTS_DIR:?Set PROJECT_RESULTS_DIR to retained storage}"
    mkdir -p "$archive_dir"
    cp results.dat "$archive_dir/"
    status=$?
    [ "$status" -eq 0 ] && echo "Results copied to retained storage"
fi

exit "$status"
